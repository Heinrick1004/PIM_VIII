RESUMO

Este trabalho apresenta o desenvolvimento do TaskFlow para a Alunos Tech, empresa fictícia que necessita organizar e acompanhar tarefas internas com histórico de alterações. O objetivo foi integrar aplicações, dados e práticas de desenvolvimento em uma solução comum, concebida por incrementos ágeis. A arquitetura reúne uma API REST em ASP.NET Core e clientes Web MVC, Mobile com Flutter e Desktop com Windows Forms, conectados por contratos HTTP. O SQL Server, acessado pelo Entity Framework Core e por migrations, organiza usuários, tarefas e eventos de histórico com chaves e restrições de integridade. A API centraliza autenticação e autorização; transações coordenam gravações e RowVersion implementa concorrência otimista. O projeto inclui function, procedure e trigger, além de consultas paginadas. Como proposta de Cloud Computing e DevOps, foram elaborados Dockerfiles, Compose, workflow de integração contínua no GitHub Actions e manifestos Kubernetes, com verificações de saúde e configuração de escalabilidade. O gerenciamento ágil foi estruturado por backlog priorizado, histórias de usuário, critérios de aceite, sprints planejadas e diário de desenvolvimento. Os registros documentam testes de domínio e integração, validação manual do cliente Mobile e testes HTTP isolados do Desktop. O TaskFlow demonstra a integração dos conteúdos de .NET, banco de dados, aplicações multiplataforma, infraestrutura como código e gestão ágil em resposta a uma necessidade organizacional.

Palavras-chave: gestão de tarefas; API; SQL Server; .NET; DevOps.

ABSTRACT

This paper presents the development of TaskFlow for Alunos Tech, a fictional company that needs to organize and track internal tasks and their change history. The goal was to integrate applications, data, and development practices in a shared solution designed through agile increments. The architecture combines an ASP.NET Core REST API with MVC web, Flutter mobile, and Windows Forms desktop clients connected through HTTP contracts. SQL Server, accessed through Entity Framework Core and migrations, stores users, tasks, and history events with keys and integrity constraints. The API centralizes authentication and authorization; transactions coordinate writes, while RowVersion implements optimistic concurrency. The project includes a function, a stored procedure, a trigger, and paginated queries. As a Cloud Computing and DevOps proposal, it includes prepared Dockerfiles, Compose, a GitHub Actions continuous integration workflow, and Kubernetes manifests with health checks and scaling configuration. Agile project management was organized through a prioritized backlog, user stories, acceptance criteria, planned sprints, and a development log. Project records document domain and integration tests, manual validation of the mobile client, and isolated HTTP tests for the desktop client. TaskFlow demonstrates how .NET, database development, multiplatform applications, infrastructure as code, and agile management can be integrated to address an organizational need.

Keywords: task management; API; SQL Server; .NET; DevOps.

1 INTRODUÇÃO

Organizações que acompanham demandas em mensagens e planilhas podem ter dificuldade para identificar o estado atual de cada atividade, acompanhar mudanças e distribuir responsabilidades. Esse cenário orienta o Projeto Integrado Multidisciplinar VIII: a empresa fictícia Alunos Tech necessita centralizar tarefas internas e registrar seu histórico. A questão que conduz o trabalho é como integrar aplicações e persistência de dados para oferecer consulta e atualização de tarefas com controle de acesso.

O objetivo geral é desenvolver e documentar o TaskFlow como uma solução acadêmica integrada, articulando programação .NET, banco de dados, Cloud Computing e DevOps e gerenciamento ágil. Para isso, foram estruturados uma API e clientes Web, Mobile e Desktop; um modelo relacional para usuários, tarefas e histórico; mecanismos de autenticação, autorização e concorrência; e configurações declarativas de infraestrutura e automação.

A metodologia foi incremental e guiada por requisitos funcionais e não funcionais, histórias de usuário e critérios de aceite. O desenvolvimento organizou regras de domínio, persistência e serviços HTTP, conectou os clientes à API e registrou atividades e verificações. A documentação relaciona a estrutura do código, as migrations, os testes registrados e os artefatos de infraestrutura, distinguindo implementação de configurações propostas para evolução em nuvem.

O texto apresenta o contexto e a arquitetura integrada, o desenvolvimento dos clientes, a modelagem e a programação do banco de dados, a proposta de Cloud Computing e DevOps, a organização ágil e os resultados documentados. A conclusão reúne as contribuições técnicas do TaskFlow e a integração entre as disciplinas em torno da necessidade de organizar e acompanhar tarefas.

2 ANÁLISE E ARQUITETURA DA SOLUÇÃO

2.1 Contexto organizacional

A Alunos Tech é a empresa fictícia definida para este PIM VIII. O cenário considerado é o de uma equipe que distribui demandas internas e precisa acompanhar responsáveis, prazos, prioridades e decisões. Quando essas informações ficam em canais distintos, torna-se mais difícil recuperar o estado de uma tarefa e seu histórico. O TaskFlow foi concebido para reunir esses dados em uma plataforma acessível por diferentes clientes.

O escopo funcional contempla usuários com perfis Administrador e Funcionário, tarefas com título, descrição, prioridade, prazo e status, identificação de criador e responsável e histórico de alterações. O administrador cadastra e distribui tarefas; o funcionário acompanha aquelas em que participa e, quando designado, atualiza seu status. A API aplica as regras de acesso nas operações correspondentes.

O backlog relaciona histórias de usuário aos requisitos e critérios de aceite, traduzindo o cenário organizacional em comportamentos claros para a solução. A plataforma mantém uma fonte compartilhada de dados e regras: as interfaces apresentam os fluxos adequados a cada dispositivo, enquanto usuários, tarefas, histórico e autorização permanecem integrados pelo serviço central.

A proposta atende ao escopo acadêmico ao conectar a necessidade de coordenação da Alunos Tech a funções concretas de consulta, distribuição e acompanhamento. Dessa forma, cada disciplina contribui para o mesmo objetivo: oferecer uma base organizada para o trabalho cotidiano e preservar a rastreabilidade das mudanças.

3 DESENVOLVIMENTO DAS APLICAÇÕES

3.1 API, autenticação e autorização

A API ASP.NET Core expõe recursos de autenticação, usuários e tarefas. No login, recebe as credenciais, valida o hash armazenado e emite um token JWT assinado, configurado com parâmetros de emissor, público e chave fornecidos pelo ambiente. O endpoint /api/auth/me permite consultar a identidade autenticada. A configuração sensível permanece fora do código-fonte; o seeder de demonstração é optativo e condicionado ao ambiente Development e às variáveis configuradas.

Os contratos da API abrangem criação e edição administrativa, consulta paginada, detalhes, histórico, resumo e mudança de status. A identidade do autor deriva das claims validadas. As políticas permitem ao administrador gerenciar tarefas e usuários e restringem ao funcionário os dados das tarefas em que participa. Detalhes, histórico e mudança de status aplicam as verificações de vínculo documentadas.

As consultas aplicam o escopo de visibilidade antes da contagem e da paginação. Os filtros incluem status, prioridade, responsável, ausência de responsável e título, com limites para os parâmetros de página. DTOs definem os dados de entrada e saída, enquanto validações de domínio e servidor protegem os campos e enumerações. O resumo utiliza procedure parametrizada.

A atualização de status transmite a RowVersion recebida pelo cliente. Se outra operação modificar a tarefa primeiro, a API responde com HTTP 409 e preserva a gravação concorrente já realizada. Esse mecanismo informa o conflito e permite atualizar os dados antes de uma nova decisão, evitando sobrescrita silenciosa. Erros de autenticação e autorização são comunicados por respostas 401 e 403.

3 DESENVOLVIMENTO DAS APLICAÇÕES

3.2 Interface Web ASP.NET Core MVC

O cliente Web foi desenvolvido com ASP.NET Core MVC e Razor. Controllers recebem formulários, chamam um serviço HTTP tipado e encaminham modelos às views. A interface reúne login, painel, listagem e filtros de tarefas, detalhes e histórico, além de formulários administrativos para tarefas e usuários. A camada visual utiliza a API e não acessa diretamente o contexto do Entity Framework Core.

Após a autenticação pela API, o MVC guarda o JWT em ticket protegido pelo ASP.NET Core Data Protection e utiliza cookie de sessão. O token não é exposto em campos do formulário nem ao JavaScript. O logout encerra a sessão local, e formulários que alteram dados aplicam proteção antiforgery. As configurações para ambiente externo preveem HTTPS e persistência segura do key ring entre reinicializações e réplicas.

As respostas da API são tratadas de acordo com seu significado: sessão expirada retorna ao login, falta de permissão apresenta acesso negado, e falhas de conexão ou conflitos recebem mensagens próprias. Registros de desenvolvimento incluem testes de controllers e renderização em ambiente de preview, além da revisão da navegação e de diferentes larguras de tela.

O endereço da API é configurável por ambiente. O perfil local permite HTTP para desenvolvimento; a configuração externa utiliza HTTPS, origem permitida e chaves persistentes. Assim, o cliente Web compartilha o contrato da API e mantém a responsabilidade pela apresentação, enquanto autenticação e autorização permanecem centralizadas no serviço.

3 DESENVOLVIMENTO DAS APLICAÇÕES

3.3 Cliente Mobile Flutter

O aplicativo Mobile foi desenvolvido em Dart com Flutter para Android, oferecendo acesso às tarefas pela mesma API utilizada pelos demais clientes. Seus fluxos incluem autenticação, gerenciamento de sessão, consulta, visualização de detalhes e atualização de status. A integração usa HTTP, endereço configurável e modelos próprios para as respostas, sem acesso direto ao SQL Server.

O token da sessão é mantido em armazenamento seguro de plataforma. A API verifica assinatura, validade, perfil e vínculo com a tarefa em cada operação; os controles apresentados na interface orientam a navegação e complementam as respostas de autorização do servidor. O tratamento de falhas de rede e das respostas 401, 403 e 409 torna explícito o resultado das solicitações.

O diário de desenvolvimento registra uma validação manual no emulador Android com login, perfil, listagem, detalhes, histórico e restauração de sessão por adb reverse. Essa validação documentada integra as evidências do cliente Mobile e demonstra seu fluxo de comunicação com a API no ambiente utilizado.

O aplicativo amplia os pontos de acesso ao TaskFlow sem duplicar regras de negócio. A compatibilidade entre modelos, rotas e respostas é mantida pelo contrato HTTP compartilhado, enquanto a interface móvel apresenta as ações pertinentes à rotina de consulta e acompanhamento de tarefas.

3 DESENVOLVIMENTO DAS APLICAÇÕES

3.4 Cliente Desktop WinForms

O cliente Desktop utiliza Windows Forms com .NET 10 e mantém a integração com a API por um serviço HTTP próprio. A janela organiza login, lista de tarefas, detalhes, histórico e mudança de status. Modelos de API representam as respostas, e o serviço encapsula rotas, cabeçalhos bearer e interpretação dos códigos HTTP. O token permanece em memória durante a sessão.

No login, a aplicação inicia a sessão após receber resposta válida da API. Respostas 401 e 403 informam, respectivamente, que a autenticação não foi aceita ou que a operação não está autorizada. Falhas de conexão comunicam a indisponibilidade do serviço, e HTTP 409 indica conflito de versão para que os dados sejam atualizados. O logout limpa a sessão e os dados apresentados.

A lista exibe as tarefas disponíveis ao usuário autenticado; a seleção consulta detalhes e histórico pelo identificador. A atualização de status envia o valor Base64 de RowVersion recebido da API. Assim, o cliente Desktop aplica o mesmo controle de concorrência e as mesmas permissões que os outros pontos de acesso, sem conexão direta ao banco.

Os registros de implementação documentam a compilação do cliente sem avisos ou erros e sete testes HTTP isolados sobre a interpretação de respostas da API. A separação entre tela, serviço HTTP e DTOs mantém o código desacoplado da persistência e permite evoluir a interface preservando os contratos da solução.

4 PROGRAMAÇÃO DE BANCO DE DADOS

4.1 Modelo relacional e integridade

O SQL Server persiste três entidades centrais: Usuarios, Tarefas e HistoricoTarefas. Usuario contém identificador, nome, e-mail, hash de senha e perfil. Tarefa reúne título, descrição, status, prioridade, datas UTC, criador, responsável opcional e RowVersion. HistoricoTarefa registra tarefa, autor, ação, data e descrição. As relações permitem que usuários criem e acompanhem tarefas com vários eventos associados.

As configurações do Entity Framework Core definem tipos e limites compatíveis com as regras de domínio. E-mail possui índice único com comparação sem distinção entre maiúsculas e minúsculas; constraints CHECK limitam valores de enum e campos obrigatórios. GUIDs identificam registros, datas usam UTC e datetime2, e chaves estrangeiras preservam integridade referencial sem exclusão em cascata. Migrations versionam a evolução do schema.

A integridade também é aplicada na camada de domínio, que valida e-mail e limites de texto, normaliza entradas e verifica datas. A aplicação calcula o hash da senha antes da persistência e não o inclui nos DTOs. O banco protege a consistência estrutural; a API aplica as regras de acesso aos dados.

A unidade de trabalho coordena as gravações de tarefa e histórico. A criação e seu primeiro evento são confirmados na mesma transação; alterações efetivas geram eventos associados, e operações sem mudança de valor evitam duplicidade. O histórico é disponibilizado em consulta paginada, o que facilita acompanhar a evolução da atividade.

4 PROGRAMAÇÃO DE BANCO DE DADOS

4.2 Função, procedure, trigger e transações

A migration AddTaskFlowProgrammability define dbo.fn_TarefasVisiveis, dbo.usp_TarefasResumo e dbo.TR_Tarefas_ProtegeDadosCriacao. A função tabular retorna tarefas criadas pelo usuário ou atribuídas a ele sem duplicar registros. A procedure recebe identidade e perfil administrativo, calcula totais por status e aplica a função para limitar o resumo do funcionário. A listagem principal usa consultas LINQ traduzidas para SQL, e o resumo consome a procedure parametrizada.

A trigger AFTER UPDATE compara as tabelas inserted e deleted e protege CriadorId e CriadaEmUtc contra alterações. O erro 51001 identifica a tentativa de modificar esses dados de criação. A regra é aplicada também a atualizações com múltiplas linhas; os demais campos permanecem editáveis segundo as operações previstas. A trigger complementa as validações da aplicação e não substitui o registro de histórico.

As transações da infraestrutura agrupam a gravação de tarefas e seus eventos. Em caso de falha intermediária, rollback mantém a consistência entre os registros; na atualização concorrente, o evento da operação rejeitada não é confirmado. As migrations criam e removem function, procedure e trigger de forma rastreável, respeitando a ordem de dependência (MICROSOFT, s.d.-c).

Os registros de 13/11/2026 documentam 123 testes aprovados na suíte integrada, incluindo cenários de function, procedure, trigger, transação, RowVersion e chamadas HTTP com SQL Server isolado. Esse resultado histórico registra a verificação dos objetos programáveis e dos fluxos de persistência no ciclo de desenvolvimento.

4 PROGRAMAÇÃO DE BANCO DE DADOS

4.3 Consultas, desempenho e concorrência

As consultas de tarefas, usuários e histórico aplicam filtros no servidor, contam resultados antes da paginação e usam Skip/Take com ordenação determinística. Rotas de leitura utilizam AsNoTracking quando as entidades não serão editadas no contexto. A paginação limita o volume de dados materializado por solicitação; os parâmetros de tarefas e histórico aceitam até 100 itens por página. A documentação do Entity Framework Core recomenda consultas ajustadas aos dados necessários e à execução real (MICROSOFT, s.d.-d).

O modelo inclui o índice composto IX_Tarefas_Status_ResponsavelId e índices para chaves primárias, estrangeiras e e-mail. A ordenação por data e identificador fornece desempate estável. O filtro por substring atende à busca de título prevista no escopo; sua eficiência em diferentes volumes pode ser avaliada por plano de execução e carga representativa antes de selecionar estratégias adicionais.

RowVersion é um token binário de oito bytes gerado pelo SQL Server. O EF Core compara a versão original enviada pelo cliente com o valor armazenado; se outra transação tiver vencido, a API retorna HTTP 409. O token trafega em Base64 no contrato HTTP e representa concorrência otimista, não um contador de negócio (MICROSOFT, s.d.-e; MICROSOFT, s.d.-f).

A identidade e as permissões são verificadas antes das consultas. Comandos SQL utilizam parâmetros tipados, e a procedure é chamada como stored procedure. Índices, paginação, filtros e RowVersion formam a base de consistência e acesso aos dados implementada no projeto; a avaliação quantitativa de capacidade depende de medições com carga representativa.

5 CLOUD COMPUTING E DEVOPS

5.1 Topologia proposta e conteinerização

A arquitetura proposta para Cloud Computing separa API e MVC em imagens .NET que podem ser executadas em Kubernetes gerenciado atrás de Ingress com TLS. O SQL Server permanece como serviço externo acessível por rede privada. Conexão, emissor, público e chave JWT são parâmetros do ambiente; o repositório contém exemplos de configuração sem credenciais reais. Logs estruturados são preparados para integração com os mecanismos de coleta do provedor.

Os Dockerfiles seguem estratégia multi-stage: SDK para restauração e compilação e runtime para execução da aplicação publicada, reduzindo dependências na imagem final (DOCKER, s.d.). Os containers definem usuário não privilegiado, portas e verificações de saúde. O Compose descreve a execução local de API e MVC e utiliza uma instância SQL Server configurada no ambiente.

Os endpoints /health e /ready oferecem sinais distintos. O primeiro verifica a disponibilidade do processo; o segundo verifica a dependência do banco e informa quando a aplicação está pronta para receber solicitações. A configuração do MVC prevê persistência protegida do key ring Data Protection para uso entre reinicializações e réplicas.

Esses Dockerfiles, o Compose e a topologia de serviços constituem artefatos declarativos de implantação preparados no projeto. Sua aplicação em nuvem utiliza os parâmetros, recursos de rede, armazenamento e segredos definidos pelo ambiente provedor, mantendo separados o código da aplicação e a configuração operacional.

5 CLOUD COMPUTING E DEVOPS

5.2 CI, Kubernetes e escalabilidade

O workflow GitHub Actions organiza restore, build e testes .NET em Windows, compatível com o cliente WinForms, e a construção das imagens da API e do Web em Linux. A estrutura segue as etapas recomendadas para automação de aplicações .NET e conecta integração contínua aos arquivos versionados do projeto (GITHUB, s.d.).

Os manifestos Kubernetes definem namespace, ConfigMap, serviços, Ingress TLS, PVC e deployments para API e Web. Contexto de segurança e solicitações de CPU e memória descrevem os recursos de execução. Readiness e liveness usam endpoints distintos, e os Horizontal Pod Autoscalers definem parâmetros para escala horizontal conforme utilização de CPU, com suporte de métricas do cluster (KUBERNETES, s.d.-a; KUBERNETES, s.d.-b).

Para compor o ambiente, os manifestos preveem imagens em registry, secrets gerenciados, domínio e certificado TLS, Ingress class e StorageClass compatível com o PVC. As chaves Data Protection, acesso ao SQL Server e políticas de rede também integram a configuração de segurança. A automação de migrations permanece supervisionada e vinculada ao ciclo de implantação.

O conjunto descreve em código a integração contínua e a topologia de orquestração planejadas para o TaskFlow. Com os recursos do provedor e do cluster configurados, esses artefatos oferecem uma base para construir, observar e escalar os serviços; a expansão de réplicas é considerada junto à capacidade do banco, à sessão compartilhada e à segurança das credenciais.
